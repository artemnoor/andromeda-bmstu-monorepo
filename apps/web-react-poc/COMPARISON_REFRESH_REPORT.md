# Переработка сравнения программ — 11 октября 2026

## План выполнения

1. Сохранить исходную production-сборку, проверить текущий экран и сетевой путь.
2. Переработать поступление, подписи программ и мобильное представление всех таблиц.
3. Ускорить повторные переходы; независимо показывать уже проверенные условия приёма.
4. Проверить release consistency, неизвестные значения, источники, отмену и повтор.
5. Проверить браузеры/ширины, провести последовательные измерения production-сборок.
6. Независимый аудит, публикация в существующий React preview в Казахстане и проверка сайта.

## Решение

Существующий единый API adapter и read-only endpoints сохранены. Новый backend endpoint не требуется для этой переработки. Сохраняются предыдущие изменения главной, навигации, профтеста и классификаций.

- Компактная шапка страницы, полные названия выбранных программ, переходы к разделам.
- Поступление: крупные числа, отдельные строки общего конкурса и квот; год/уровень каждого балла сохраняются.
- На узких экранах таблицы превращаются в подписанные строки/блоки. Все значения остаются доступны без горизонтальной прокрутки страницы.
- Неподтверждённые места не показываются основным количеством выбранной программы: исходные предложения доступны отдельно в раскрываемом блоке. Нули сохраняются, неизвестное количество называется явно.
- Диаграммы, категории, диалог дисциплин, нагрузка и фильтры адаптированы к узким экранам. Суммы и academic joins не изменены.
- Условия приёма могут появиться раньше учебных планов. Перед показом этой секции выполняется отдельная проверка активного release; полная готовность отмечается только после финальной проверки.
- В памяти вкладки хранятся только завершённые, проверенные чтения учебных планов/строк/таксономии. Ключ включает release, кэши ограничены 8/8/2 записями. Ошибки и неполные страницы не кэшируются; отмена транспорта остаётся локальной навигации.
- Для существующего Nginx preview добавлено gzip-сжатие публичных JSON/JS/CSS без изменения payload после декодирования, маршрутов API и прав доступа.

## Методика

Сценарий: один и тот же опубликованный release, три программы 01.03.02-01 / 01.03.03-03 / 01.03.03-02, production SPA, Chromium, 1440×900. После отброшенного прогрева — 10 последовательных измерений. Для каждого — новый browser context без кэша, затем возврат в сравнение через каталог в той же вкладке. Сохраняются сырые JSON.

`firstUsefulMs` и `readyMs` фиксируются MutationObserver по появлению проверенной секции приёма и финальной отметки release. Это готовность DOM, а не отдельное измерение времени отрисовки или paint. Число повторов не позволяет делать устойчивые production p95 claims. Внешний API/сеть остаются источником вариативности; SQL duration отдельно в этой задаче не измерялся.

Исходная сборка заморожена в `artifacts/comparison-before-build`. Для неё используется `scripts/preview-comparison-build.mjs` с `configFile:false`: React Router plugin перезаписывал `--outDir` стандартного Vite preview. Прерванные пробные прогоны до обнаружения этого не используются.

## Измеренные результаты

Две последовательные серии по 10 повторов на одном компьютере, с тем же облачным API. Это сравнение пользовательского сетевого пути через локальный production preview; SQL latency из этих чисел не выводится. Серия after включает gzip на существующем облачном Nginx и кэширование завершённых чтений в React. После серии сделано небольшое UX-дополнение: карточки выбранных программ публикуются ещё до admission, сразу после проверенного каталога; критерии готовности admission/полного сравнения не менялись.

| Метрика | Before | After |
|---|---:|---:|
| Полная готовность DOM, медиана | 12 234 мс | 5 518 мс |
| Готовность секции поступления, медиана | 12 234 мс | 5 243 мс |
| Возврат через каталог, медиана | 6 668 мс | 2 434 мс |
| API payload, холодный контекст | 2 156 129 байт | 225 821 байт |
| API requests, холодный контекст | 32 | 33 |
| API requests при возврате | 13 | 4 |
| API payload при возврате | 800 737 байт | 1 460 байт |
| Расчёт curriculum model, медиана | 4,60 мс | 4,65 мс |

API payload — `encodedBodySize`, без HTTP-заголовков. Холодный запрос дополнительно проверяет release перед показом admission, поэтому число HTTP-запросов увеличилось на один. Сжатие сократило payload примерно на 89,5%; повторная загрузка планов исключена. Время возврата включает одинаковый путь через меню каталога, а не только API.

Сырые результаты: [before](benchmarks/comparison-refresh-before.json), [after](benchmarks/comparison-refresh-after.json). Все 10 before имеют одинаковые 32 запроса и одинаковый размер payload. After дополнительно сохраняет release, ключи программ/планов, количество строк и суммы часов каждого sample и проверяет отсутствие недоступных admission данных. Во всех повторениях используются полные, одинаковые данные; необходимая информация не исключалась.

Сетевые задержки остались: cold after — от 2,48 до 20,78 с. Цель 1 800 мс для этого внешнего пути не достигнута. Причина отдельных длительных обращений к облачному API пока не локализована между транспортом и серверным выполнением; утверждать, что нестабильность полностью устранена, нельзя. Значения стадий — отдельные медианы, складывать их для получения общей медианы некорректно.

## Корректность и проверки

- `npm run typecheck`, `npm run lint`, `npm test`: успешно, 92 Vitest tests.
- `npm run api:check`: OpenAPI и TypeScript DTO актуальны.
- `npm run build`: production SPA собран успешно.
- Новые API regression tests: reuse завершённых чтений, смена active release при cached reads, retry неполного плана, admission preview до медленного curriculum, запрет cross-release preview, отмена до preview, раннее появление выбранных программ.
- Admission regression tests: related facts отдельно от подтверждённых мест/квот, zero/null, строгие direction/department/campus связи, запрещённые чужие предложения, подписи кафедр и полного имени программы, отсутствие совпадения ИУ1 с ИУ11. Старые expected не менялись.
- Gzip: ответ `/programs?limit=100` — 454 521 → 67 392 байт; распакованный ответ побайтно совпадает с identity-response (SHA-256 `7e40cd33e0971c26b40d296cd40c2c04b81206e21dfc876e3766fcb3c0218c3d`).
- Облачный E2E-прогон выявил отдельные превышения существующего 15-секундного ожидания. Проверки не ослаблялись; функциональный прогон перенесён на локальный API с PostgreSQL 16 и тем же release. Первый локальный запуск использовал порт 4190, запрещённый Firefox; исправлено окружение — порт 4184, без обхода браузерной защиты.
- Regression отмены: уже отменённый signal не запускает fetch. При hard reload незавершённая загрузка отменяется в `beforeunload` (listener снимается после завершения), `pagehide` также отменяет; возврат из BFCache запускает новую проверку release. WebKit раньше продолжал API-chain при выгрузке документа и выдавал access-control pageerrors для same-origin URL. Исправление прошло три последовательных повтора прежнего persistence-теста, без фильтрации CORS ошибок или изменения его ожиданий. Только стандартное сообщение WebKit `Load request cancelled` добавлено к существующим эквивалентам AbortError в request diagnostics.
- Финальный Playwright на итоговой production-сборке: **19 passed, 2 skipped**, 3,9 минуты; Chromium, Firefox, WebKit. Два skip предусмотрены существующим scale-тестом для Firefox/WebKit; измерение 100/500/1000 строк выполнено в Chromium. Все live и responsive сценарии прошли во всех трёх браузерах. Ожидания данных и существующие timeouts не менялись.

Сравнение часов/числа строк и владения curriculum выполняется существующими live-тестами по независимо прочитанным API-данным. Новый responsive сценарий проверяет две/три программы на 320, 390, 600, 768, 1024, 1440 px, отсутствие горизонтального переполнения, диалог категорий, фильтры и переключение нагрузки. Scale-сценарий проверяет 100/500/1000 строк. Скриншоты сохраняются в Playwright artifacts; старый pixel-parity с Vanilla не использован как критерий для разрешённого пользователем редизайна. Vanilla и остальные страницы в этой задаче не менялись.
